## ✅ Шаг 5: Создание заказа — POST /orders
- Принимает `route` и `comment` (опциональны)
- Создаёт `Order` со статусом `pending`
- Уточнение: сразу создаёт `OrderOffer` для первого в очереди
  (см. ARCHITECTURE.md)
- Проверено локально через `/docs`

## ✅ Шаг 6: Принятие/отказ — POST /orders/{id}/respond
- Принимает `user_id` и `response` (`accepted`/`declined`)
- При `accepted`: заказ назначается, пользователь сразу уходит в конец очереди
- При `declined`: оффер уходит следующему по очереди (по кругу)
- Проверено локально через `/docs`, оба сценария корректны

## ✅ Шаг 7: Завершение заказа — POST /orders/{id}/complete
- Проверяет `Order.status == assigned`, иначе `400`
- При успехе: `status -> completed`, `completed_at = now()`
- Рефакторинг ошибок: переход на `HTTPException` вместо `{"error": ...}`
  (см. ARCHITECTURE.md)
- Проверено локально через `/docs` и `curl`, все edge-кейсы корректны

## ✅ Шаг 8: История заказов — GET /orders

- Сортировка `created_at DESC`, без полноценной пагинации

- **Побочный баг, найденный и исправленный по пути:** `_log_activity`
  коммитит сессию, что инвалидирует (`expire`) уже загруженный объект
  `order`/`item` в SQLAlchemy; при возврате такого объекта как
  `response_model` FastAPI сериализовал его в пустой `{}` без ошибки
  (Pydantic v2 берёт значения из `__dict__` инстанса, а `expire` их
