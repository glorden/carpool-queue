- Проверено локально через `/docs` — заказ создаётся корректно,
  возвращается с присвоенным `id`
  
## Уточнение к Шагу 5 / подготовка к Шагу 6
- POST /orders теперь при создании заказа сразу создаёт OrderOffer
  для первого пользователя в очереди (раньше договаривались, что это
  будет отдельным шагом — по факту оказалось логичнее делать сразу,
  т.к. заказ без предложения первому не имеет смысла как отдельное
  состояние)
- Проверено локально: после создания заказа в таблице order_offer
  появляется запись с response=pending для того, кто сейчас первый
  по очереди

## ✅ Шаг 6: Принятие/отказ — POST /orders/{id}/respond
- Добавлен эндпоинт POST /orders/{order_id}/respond в app/main.py
- Принимает user_id и response ("accepted" или "declined")
- Находит актуальный pending-OrderOffer для заказа
- При accepted: OrderOffer -> accepted, Order.status -> assigned,
  Order.assigned_to = user_id, **пользователь сразу уходит в конец очереди**
  (максимальная позиция + 1) — важно: перемещение происходит именно
  в момент принятия заказа, а не в момент его завершения. Это осознанное
  решение: пока человек не закончит текущую поездку, следующий заказ уже
  пойдёт другому — иначе новый заказ мог бы снова прийти тому, кто уже занят
- При declined: OrderOffer -> declined, Order остаётся pending,
  автоматически создаётся новый OrderOffer для следующего по очереди
  (по кругу, если отказавшийся был последним)
- Проверено локально через /docs: и accepted, и declined отработали
  корректно, очередь и статусы заказа меняются как задумано

## ✅ Шаг 7: Завершение заказа — POST /orders/{id}/complete
- Добавлен эндпоинт `POST /orders/{order_id}/complete` в `app/main.py`
- Без параметров в теле запроса — просто помечает заказ завершённым
- Проверяет, что `Order.status == assigned`, иначе `400 Bad Request`
  (нельзя завершить заказ, который ещё не назначен или уже завершён)
- Если заказа не существует — `404 Not Found`
- При успехе: `Order.status -> completed`, `Order.completed_at = now()`
- "Кто завершил" отдельно не спрашивается — эта информация уже есть
  в `Order.assigned_to` (зафиксирован на этапе `accept`)
- `OrderOffer` не трогается — история предложений (`offered_at`,
  `responded_at`) уже полностью сохранена с Шага 6, этого достаточно
- Очередь не трогается — перемещение туда уже произошло на этапе `accept`
- Проверено локально через `/docs` и `curl`: успешное завершение,
  повторное завершение, завершение несуществующего заказа, завершение
  ещё не назначенного заказа — все сценарии дают ожидаемый результат

## ✅ Шаг 8: История заказов — GET /orders
- Добавлен эндпоинт `GET /orders` в `app/main.py`
- Опциональные query-параметры:
  - `status` — фильтр по статусу заказа
  - `user_id` — фильтр по исполнителю (`Order.assigned_to`)
  - `limit` — максимум записей в ответе (default=100, ограничен `le=500`
    через `Query`, чтобы нельзя было запросить неограниченный объём)
- Сортировка: `created_at DESC` (новые заказы сверху) — сделано дефолтным
  поведением, отдельного параметра под сортировку не вводили
- Полноценную пагинацию (offset, total count) решили пока не делать —
  при масштабе 10 человек/несколько сотен заказов это лишняя сложность;
  `limit` достаточно как простая страховка
- OrderOffer по каждому заказу не подтягивается — `GET /orders` возвращает
  плоский список `Order`, единообразно с `/respond` и `/complete`. Если
  понадобится детальная история предложений — отдельный эндпоинт позже
  (например, `GET /orders/{id}/offers`)
- Проверено локально через `curl`: без фильтров, `?status=completed`,
  `?user_id=1&limit=5` — все три сценария вернули ожидаемые результаты

## Рефакторинг ошибок (Шаг 7): переход на HTTPException
- Все три эндпоинта (`create_order`, `respond_to_order`, `complete_order`)
  переведены с `return {"error": "..."}` на `raise HTTPException(...)`
- Причина: при `response_model=Order` FastAPI пытался силой привести
  словарь `{"error": ...}` к модели `Order`, из-за чего в ответе вместо
  сообщения об ошибке возвращался "пустой" фейковый Order со всеми
  полями `null`/дефолтами — ошибка терялась
- Теперь ошибки возвращаются в стандартном формате FastAPI:
  `{"detail": "..."}` с корректным HTTP-статусом (`404` — не найдено,
  `400` — некорректное состояние/запрос)
- Это меняет формат ответа для будущего клиента/фронтенда — учитывать
  при реализации Шага 9 (HTML-интерфейс)

## Архитектурные решения и упрощения
- **POST /orders/{id}/respond (Шаг 6):** эндпоинт НЕ проверяет, что отвечает
  именно тот пользователь, которому реально было отправлено предложение
  (нет проверки "это твоя очередь"). Любой user_id может принять/отклонить
  любой pending-заказ. Осознанное упрощение: группа доверенных людей (10 чел),
  договорённости идут в личном чате, риск злоупотребления минимален.
  Если понадобится ужесточить — добавить проверку активного OrderOffer
  с response=pending именно для этого user_id.
- **POST /orders/{id}/complete (Шаг 7):** аналогично — эндпоинт НЕ проверяет,
  что вызывает именно тот, кому назначен заказ (`assigned_to`). Единообразие
  с `/respond` ради простоты; риск минимален в доверенной группе.
  Единственная проверка — что заказ в статусе `assigned` (защита от
  нелогичных переходов состояния, а не от "не того" человека).

## Технический долг (зафиксировано, не блокирует MVP)
- Отсутствие проверки identity в `/respond` и `/complete` (см. раздел выше)
  остаётся сознательным упрощением для текущего масштаба, но зафиксирован
  чёткий план по устранению:
  - **Решено сделать после Шага 9** (HTML-интерфейс), а не сейчас — по двум причинам:
    1. Сейчас тестирование ведётся вручную через `curl`, лишняя проверка
       мешала бы быстрым ручным тестам
    2. Фронтенд прояснит, откуда реально будет браться `user_id` на клиенте
       (сессия, выбор из списка, что-то ещё) — это может повлиять на форму проверки
  - План:
    - `/respond`: фильтровать `OrderOffer` сразу по `user_id` (не только по
      `order_id` + `pending`), возвращать `403`, если для этого `user_id`
      нет pending-оффера
    - `/complete`: добавить тело запроса с `user_id`, проверять
      `order.assigned_to == user_id`, иначе `403`
    - **Важно:** это меняет контракт `/complete` — сейчас эндпоинт вызывается
      без тела запроса, после изменения тело станет обязательным. Учесть
      при разработке фронтенда на Шаге 9

## 🔄 Шаг 9: Простой интерфейс (HTML) — обсуждены и зафиксированы решения

Перед началом реализации обсудили и зафиксировали архитектуру фронтенда:

- **Структура страниц:** дэшборд (очередь + индикатор активного предложения +
  форма создания заказа) — на одной странице. История заказов — отдельная
  страница (таблица + фильтры status/user_id, переиспользуем то, что уже
  есть в `GET /orders`)
- **"Кто я":** без полноценной авторизации. Селектор пользователя в шапке,
  выбор сохраняется в браузере (`localStorage`), дальше все действия
  (принять/отклонить/завершить) идут от выбранного `user_id` автоматически,
  без повторного выбора на каждое действие
- **Технология:** обычный HTML + vanilla JS, без шаблонизаторов (Jinja2
  и т.п.). JS дёргает `fetch()` к уже готовому API (Шаги 5–8), бэкенд
  почти не трогаем — фронтенд отдельный слой поверх готовых эндпоинтов
- **Индикатор "кому сейчас предложен заказ":** нужен явно в интерфейсе,
  не только через `/docs`

### Дополнительно нужно на бэкенде
Текущий `GET /orders` отдаёт только сам `Order`, без данных о том, кому
именно предложен активный (`pending`) заказ — этой информации нет ни в одном
эндпоинте. Для индикатора на дэшборде нужен новый read-only эндпоинт:

- `GET /orders/pending` — заказы со статусом `pending` вместе с данными
  активного `OrderOffer` (кому предложен, когда). Аддитивное изменение,
  ничего существующего не ломает

## Логика очереди (напоминание, чтобы не забыть при разработке)
- Заказ предлагается первому в очереди
- Принял → **сразу уходит в конец очереди** (не дожидаясь завершения поездки)
- Выполнил → отдельно помечается через `/complete` (статус, время)
- Отказался → остаётся на своей позиции, заказ уходит следующему
- Таймаутов на ответ нет — ждём сколько угодно, коммуникация идёт в личном чате участников
