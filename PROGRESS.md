# Прогресс проекта Carpool Queue

Здесь фиксируем, что уже сделано, чтобы не терять контекст между сессиями.
Архитектурные решения, технический долг и логика очереди — в [ARCHITECTURE.md](./ARCHITECTURE.md).

## ✅ Шаг 1: Каркас проекта
- Структура папок (`app/`, `deploy/`), минимальное FastAPI-приложение
- `requirements.txt`, `.gitignore`, `.env.example`, `README.md`
- Проверено локально: `uvicorn app.main:app --reload` → отвечает корректно
- Python 3.13.3 в venv (совпадает с версией на сервере)

## ✅ Шаг 2: Приватный репозиторий на GitHub
- Репозиторий: https://github.com/glorden/carpool-queue
- Git инициализирован, авторизация через браузер, код запушен в `main`

## ✅ Шаг 3: Модели БД + первая Alembic-миграция
- Модели: `User`, `QueuePosition`, `Order`, `OrderOffer` (`app/models/`)
- SQLModel + SQLite (`app/database.py`, `app/config.py`)
- Alembic подключён к моделям, первая миграция применена
- Проверено: все таблицы созданы в `carpool.db`

## ✅ Шаг 4: Очередь (чтение) — GET /queue
- JOIN `QueuePosition` + `User`, сортировка по `position`
- Скрипт `scripts/seed.py` для тестовых пользователей
- Проверено локально через браузер и `/docs`

## ✅ Шаг 5: Создание заказа — POST /orders
- Принимает `route` и `comment` (опциональны)
- Создаёт `Order` со статусом `pending`
- Уточнение: сразу создаёт `OrderOffer` для первого в очереди
  (см. ARCHITECTURE.md)
- Проверено локально через `/docs`

## ✅ Шаг 6: Принятие/отказ — POST /orders/{id}/respond
- Принимает `user_id` и `response` (`accepted`/`declined`)
- При `accepted`: заказ назначается, пользователь сразу уходит в конец очереди
- При `declined`: оффер уходит следующему по очереди (по кругу)
- Проверено локально через `/docs`, оба сценария корректны

## ✅ Шаг 7: Завершение заказа — POST /orders/{id}/complete
- Проверяет `Order.status == assigned`, иначе `400`
- При успехе: `status -> completed`, `completed_at = now()`
- Рефакторинг ошибок: переход на `HTTPException` вместо `{"error": ...}`
  (см. ARCHITECTURE.md)
- Проверено локально через `/docs` и `curl`, все edge-кейсы корректны

## ✅ Шаг 8: История заказов — GET /orders
- Query-параметры: `status`, `user_id`, `limit` (default=100, max=500)
- Сортировка `created_at DESC`, без полноценной пагинации
- Проверено локально через `curl`: без фильтров и с разными комбинациями

## ✅ Шаг 9.1: GET /orders/pending (бэкенд)
- Read-only эндпоинт: `pending`-заказы + данные активного `OrderOffer`
- Аддитивное изменение, ничего не сломало
- Проверено вручную через `curl` полным сценарием (создание → отклонение →
  переход оффера → принятие → уход из очереди)

## ✅ Шаг 9.2: подключение статики в FastAPI
- `app.mount("/static", StaticFiles(...), name="static")`
- Структура папок `static/`, `static/css/`, `static/js/`
- Проверено: `GET /static/` отдаёт HTML, `GET /` — health-check JSON

## ✅ Шаг 9.3: дэшборд

Реализован по мини-шагам:

- ✅ **9.3.1** — HTML-каркас, селектор пользователя (`localStorage`),
  вывод очереди из `GET /queue`, подсветка текущего пользователя
- ✅ **9.3.2** — форма создания заказа (`POST /orders`), список активных
  предложений (`GET /orders/pending`), обновление без перезагрузки страницы

  адресован выбранному пользователю) и завершить (список "мои заказы
  в пути" через `GET /orders?status=assigned&user_id=X`)

## ✅ Шаг 9.4: страница истории заказов

- Создана `static/history.html` — отдельная страница с таблицей всех заказов
- Фильтры: `status` (select с вариантами pending/assigned/completed/unassigned)
  и `user_id` (select с именами из `GET /queue`), применяются кнопкой
- Таблица использует уже готовый `GET /orders` с query-параметрами,
  бэкенд не менялся
- Взаимные ссылки между дэшбордом и историей в шапке ("История заказов →" / "← Дэшборд")
- Проверено: фильтры по отдельности и вместе работают корректно
