# Архитектура и решения — Carpool Queue

Здесь фиксируем решения, которые живут дольше одного шага: логику,
которую нельзя менять не подумав, зафиксированный технический долг
и стек технологий. Хронология выполненных шагов — в [PROGRESS.md](./PROGRESS.md).

## Стек технологий

Ubuntu Server, Caddy, Python 3.13, FastAPI, SQLModel, SQLite, Alembic.
Приватный репозиторий: https://github.com/glorden/carpool-queue

## Логика очереди (ключевое бизнес-правило)

С Шага 23 в проекте две полностью независимые очереди — `QueueType.long`
(дальние/межгородние поездки) и `QueueType.short` (короткие). Один и тот
же водитель может состоять в обеих одновременно (`QueuePosition`
уникальна по паре `user_id`+`queue_type`, не по одному `user_id`).
Каждый `Order` обязан иметь `queue_type`, и вся арифметика ниже
применяется **только** к очереди этого типа — заказ дальней очереди
никогда не читает и не переставляет позиции в короткой, и наоборот.
Подробности — раздел «Две очереди» ниже.

- Заказ создаётся → сразу автоматически предлагается первому в очереди
  своего типа (создаётся `OrderOffer`)
- Принял → сразу уходит в конец очереди (не дожидаясь завершения поездки —
  иначе новый заказ мог бы снова прийти тому, кто уже занят)
- Выполнил поездку → отдельно помечается через `/complete` (статус, время)
- Отказался → остаётся на своей позиции, заказ автоматически уходит
  следующему по очереди (по кругу, если отказавшийся был последним)
- Самоназначился (`/self-assign`) на `pending`-заказ вне очереди (с
  обязательной причиной) → тот же переход, что при `accepted`: сразу
  становится исполнителем и уходит в конец очереди (`max + 1`).
  Существующая офера, если она была кому-то другому, помечается
  `declined`, чтобы не оставалась висеть — сам предложенный водитель
  свою позицию в очереди при этом не теряет
- Таймаутов на ответ нет — ждём сколько угодно, люди договариваются
  в личном чате
- Отменён (`/cancel`) → если заказ был `assigned`, водитель, взявший
  заказ, возвращается в начало очереди — но **вторым**, сразу после
  текущего первого, а не обгоняя его. Причина: если пассажир отказался
  не по вине водителя, тот не должен терять место из-за чужой отмены,
  но и не должен вытеснять того, кто честно ждёт своей очереди первым
  (проверено на реальном сценарии — см. PROGRESS.md, Шаг 13)

## Архитектурные решения и упрощения

- **`POST /orders` сразу создаёт `OrderOffer`** для первого в очереди —
  изначально планировалось отдельным шагом, но оказалось логичнее сразу:
  заказ без предложения кому-то не имеет смысла как отдельное состояние
- **`POST /orders/{id}/respond` не проверяет identity** — не проверяет,
  что отвечает именно тот, кому реально предложен заказ. Любой `user_id`
  может принять/отклонить любой `pending`-заказ. Осознанное упрощение:
  10 доверенных людей, договорённости в личном чате, риск минимален
- **`POST /orders/{id}/complete` аналогично не проверяет вызывающего** —
  единообразие с `/respond`. Единственная проверка — что заказ в статусе
  `assigned` (защита от нелогичных переходов состояния, а не от "не того"
  человека)
- **Ошибки — только через `HTTPException`**, не через `return {"error": ...}`.
  Причина: при `response_model=Order` FastAPI силой приводил словарь
  к модели, и сообщение об ошибке терялось (ответ превращался в "пустой"
  `Order` с `null`-полями). Теперь: `{"detail": "..."}` + корректный
  HTTP-статус (`404`/`400`)
- **`GET /orders` без пагинации** — только `limit` (default=100, max=500).
  При масштабе 10 человек / несколько сотен заказов offset/total считаем
  лишней сложностью
- **`GET /orders` не отдаёт `OrderOffer`** — плоский список `Order`,
  единообразно с `/respond` и `/complete`. Детальная история предложений —
  отдельный эндпоинт при необходимости (`GET /orders/{id}/offers`)
- **`POST /orders/{id}/cancel`** — отменяет заказ из `pending` или
  `assigned`; из `completed`/`cancelled` — `400`.
  Тела запроса не требует (как и `/complete`): для `assigned`-заказа
  водитель уже известен из `order.assigned_to`, идентичность
  вызывающего не проверяется — та же модель доступа, что у
  `/respond`/`/complete`. Возврат в очередь **вторым** (не первым)
  требует вставки между текущими 1-м и 2-м местом — тут, в отличие
  от ухода в конец при `accepted` (`max + 1`, коллизий не бывает),
  переиндексирует всю очередь (`position = 0, 1, 2, ...` в новом
  порядке), т.к. позиции не гарантированно идут подряд без пропусков

## Технический долг (зафиксировано, не блокирует MVP)

Отсутствие проверки identity в `/respond` и `/complete` — сознательное
упрощение для текущего масштаба. Решено устранять **после Шага 9 целиком**
(HTML-интерфейс), а не раньше — по двум причинам:
1. Сейчас тестирование ведётся вручную через `curl`, лишняя проверка
   мешала бы быстрым ручным тестам
2. Фронтенд прояснит, откуда реально будет браться `user_id` на клиенте —
   это может повлиять на форму проверки

План устранения:
- `/respond`: фильтровать `OrderOffer` сразу по `user_id` + `pending`,
  `403` если оффера для этого `user_id` нет
- `/complete`: добавить тело запроса с `user_id`, проверка
  `order.assigned_to == user_id`, иначе `403`
- **Важно:** это изменит контракт `/complete` — сейчас вызывается без тела
  запроса

**Как это проявляется в текущем UI (Шаг 9.3.3):** кнопки "Принять/Отклонить/
Завершить" в дэшборде полагаются на то, что пользователь выбрал себя
честно — бэкенд пока не проверяет разрешение на действие.

**Охват этого долга — сознательно только `/respond` и `/complete`.**
`/cancel`, `/self-assign` и `/price` (`POST`/`PUT`/`DELETE`) используют ту
же модель без identity-проверки, но за рамками плана выше:
- `/cancel` для `pending`-заказа проверять некого — у `Order` нет поля
  "кто создал", то есть нет самого понятия владельца. Для
  `assigned`-заказа можно было бы проверить `assigned_to == user_id`,
  но точечный патч только для этого случая без общей стратегии добавил
  бы несогласованность, а не решение
- `/price` — риск уже компенсирован логом изменений (`PriceLogEntry`,
  Шаг 12), а вводить понятие "владелец позиции прайса" незачем: позиции
  общие и редактируются коллективно — это осознанная модель доступа,
  а не долг

### Если появится полноценная авторизация (задел на будущее, только на бумаге)

Ничего из этого не реализовано и не запланировано — просто фиксируем
заранее, что понадобится проверить, если/когда `user_id` из тела
запроса и `localStorage` на клиенте заменится настоящим логином и
сессией (`current_user_id` из сессии, а не из тела запроса):

- Проверки понадобятся не только на `/respond`/`/complete` — а сразу
  на всех пяти местах, где их сейчас нет: `/respond`, `/complete`,
  `/cancel`, `POST/PUT/DELETE /price`
- `/cancel` для `pending`-заказа упирается в то, что `Order` не хранит,
  кто его создал — значит, вместе с авторизацией почти наверняка
  понадобится новое поле `Order.created_by`, иначе отмену
  pending-заказа так и останется не с кем сверять
- Сначала стоит решить единый механизм получения текущего пользователя
  (сессия/токен), и только потом добавлять проверки по каждому
  эндпоинту — а не переносить сегодняшнюю логику по кусочкам

## Разделение бизнес-логики и FastAPI (задел на будущее, только на бумаге)

Сейчас весь роутинг живёт в одном `app/main.py` (без `APIRouter`), а бизнес-логика
(машина состояний заказа, математика очереди, вызовы уведомлений) написана прямо
в теле хендлеров — например, `respond_to_order` и `cancel_order`. Единственное, что
уже вынесено отдельно — `app/notifications.py`. Ничего из нижеперечисленного не
реализовано и не запланировано отдельным шагом — просто фиксируем целевую структуру
на случай, когда `main.py` разрастётся дальше, чтобы новая логика с этого момента
писалась сразу в правильном месте, а не переносилась потом целиком.

- **Роутеры — это двери в систему, сервисы — сама система.** Сегодня единственная
  дверь — REST API, но со временем могут появиться другие (Telegram-бот,
  HTML-интерфейс сверх текущего, импорт из файла, интеграция с другим сервисом).
  Все они должны вызывать одни и те же методы `services`, а правила работы очереди
  и заказов — оставаться в одном месте независимо от числа дверей
- **`app/routers/*.py`** — по файлу на ресурс (`orders.py`, `queue.py`, `price.py`),
  через `APIRouter` + `include_router` в `main.py`. Чисто транспорт: разобрал вход →
  вызвал сервис → вернул ответ; `HTTPException` на валидации входа может подниматься
  и здесь
- **`app/services/*.py`** — по файлу на домен (`orders.py`, `queue.py`), функции вида
  `respond_to_order(session, order_id, user_id, response) -> Order`. Вся машина
  состояний заказа и математика очереди — здесь, не в роутере
- **Правило на будущее, а не разовая задача:** новый или изменяемый эндпоинт, где
  логика выходит за пару строк, сразу пишется как тонкий `router` + `service`-функция
- **Побочный эффект:** такие `service`-функции можно будет тестировать напрямую, без
  `TestClient`/HTTP — закроет сегодняшний пробел, где `tests/test_queue_logic.py`
  может дойти до логики очереди только через HTTP
- **Осознанно не заводим** repository-слой, DI-контейнер или иерархию кастомных
  исключений — для масштаба 10 доверенных пользователей это была бы лишняя
  сложность; `HTTPException` из сервиса — этого достаточно

## Редактирование прайса (Шаг 12)

`/price` (`POST`/`PUT`/`DELETE`) сознательно сделаны по той же модели
доступа, что и `/respond`/`/complete`: любой `user_id` может добавить,
изменить или удалить любую позицию прайса, без проверки, что это
"его" изменение. Причина та же — доверенная группа ~10 человек, а
не случайные пользователи (доступ ко всему сайту в любом случае
закрыт HTTP Basic Auth на уровне Caddy).

Компенсация риска — не запрет, а прозрачность: каждое изменение пишет
запись в `PriceLogEntry` (кто/когда/что — `old_value`/`new_value`
снэпшотами), лог виден прямо на странице «Прайс» (`GET /price/log`).
Если кто-то ошибётся или удалит не то — видно, кто и когда, откатывать
приходится вручную (отдельного undo нет — сочли лишним для этого
масштаба).

## Уведомления водителям (Шаг 14)

Когда заказ создаётся или переходит следующему по очереди (тот же
момент, когда создаётся `OrderOffer`), бэкенд шлёт сообщение в общую
беседу VK, где состоят все водители — "Заказ #12 (маршрут) предложен:
Имя".

- **Канал — VK, а не Telegram/Web Push**: у группы уже есть общая
  беседа VK, где все состоят, — это единственный канал без email/SMS
  и без личных чатов по отдельности. Сообщество добавлено в беседу
  как обычный участник (одноразовая настройка вручную), пишет через
  `messages.send` с токеном сообщества (`VK_GROUP_TOKEN`) в
  `VK_PEER_ID` (id беседы)
- **Тег водителя в сообщении** — `User.vk_id` (nullable, миграция
  `296fad1e2c65`) хранит VK id водителя. Если он известен — сообщение
  тегает его (`[id...|Имя]`), иначе просто пишет имя текстом (без
  vk_id код продолжает работать как раньше). Заполняется вручную
  (сопоставление по имени между участниками беседы и `User.name`,
  бэкофисной формы для этого нет — редкая разовая операция)
- **Ссылка на сайт** в каждом сообщении (`SITE_URL` в `.env`, по
  умолчанию `https://zakaz.glorden.ru/`) — учти, что сайт закрыт HTTP
  Basic Auth, при переходе по ссылке браузер спросит логин/пароль
- **Best-effort, не блокирует заказ** — `app/notifications.py:notify_offer`
  оборачивает вызов VK API в `try/except`, любая ошибка (нет токена,
  таймаут, VK API вернул ошибку) только логируется, само создание/
  переход заказа не откатывается и не падает
- **Конфигурация — только через `.env`** (`VK_GROUP_TOKEN`,
  `VK_PEER_ID`), оба значения опциональны: без них уведомления просто
  не отправляются, остальной сервис работает как обычно

## Бэкап базы данных (Шаг 15)

Единственный `carpool.db` на VPS — риск потери данных при случайном
удалении (например, через `/price`) или сбое диска. Решение: ежедневный
`sqlite3 .backup` через cron (`scripts/backup_db.sh`), без внешнего
хранилища — принимаем риск полной потери VPS как маловероятный для
этого масштаба.

Хранение — не просто "последние N дней", а гибрид:
- самая свежая копия хранится всегда, сколько бы времени ни прошло;
- более старые копии переживают ежедневную чистку только по сетке
  "раз в 10 дней", отсчитанной от фиксированной даты (`EPOCH` в
  скрипте) — так со временем остаются срезы за все периоды жизни
  проекта, а не только за последний месяц, и место не растёт
  бесконечно (после года — 36 файлов, а не 365)

Восстановление — вручную (см. DEPLOY.md), автоматического failover нет.

## Журнал действий (Шаг 19)

Отдельная сущность `ActivityLog` (`app/models/activity.py`), не заменяет
историю заказов (`Order`) — дополняет её хронологией событий по ходу
жизни заказа и очереди, по образцу `GET /issues` из GitHub-заявки на
эту фичу. Поля: `id`, `created_at`, `user_id` (nullable), `order_id`
(nullable), `event_type`, `message` (готовый текст для UI, не собирается
из шаблона на фронте).

- **Пишется из `app/main.py` напрямую в тех же хендлерах**, что и
  сами переходы заказа (`create_order`, `respond_to_order`,
  `complete_order`, `cancel_order`) — тем же способом, что `PriceLogEntry`
  в `/price`. Отдельного router/service под это не заводили — см. «Разделение
  бизнес-логики и FastAPI» выше, туда же попадёт при рефакторинге, если
  дойдёт до него
- **`event_type` значения:** `order_created`, `order_offered`,
  `order_accepted`, `order_declined`, `order_completed`, `order_cancelled`,
  `queue_changed` (используется дважды — уход в конец очереди при
  принятии и возврат в начало при отмене назначенного заказа)
- **`user_id` не всегда известен.** У `POST /orders`, `/complete` и
  `/cancel` нет тела запроса с id исполнителя (тот же identity-долг,
  что описан выше) — событие в этих случаях пишется с `user_id=None`,
  но с осмысленным текстом в `message`
- **`GET /activity`** — фильтры `user_id`/`order_id`/`event_type`,
  `limit` (default=100, max=500), новые сверху. Реализация — копия
  паттерна `GET /price/log`
- **Побочный баг, найденный при реализации:** запись лога сразу после
  `session.commit()` инвалидирует (`expire`) уже загруженный ORM-объект;
  если его потом вернуть как `response_model` без повторного `refresh`,
  FastAPI молча сериализует пустой `{}` вместо реальных полей (без
  ошибки, без 500). Тот же баг уже существовал в `POST/PUT /price` —
  просто был незаметен, потому что фронтенд не читает поля из ответа
  этих ручек. Исправлено добавлением `session.refresh(...)` после
  каждого коммита лога, перед `return`. Если добавляешь новый
  `_log_activity`/`PriceLogEntry`-подобный вызов после того, как объект
  уже был зарефрешен — не забудь зарефрешить его снова перед возвратом

## Самоназначение на заказ (Шаг 20)

По GitHub issue: иногда водитель уже находится в городе подачи или по
другой уважительной причине может выполнить заказ быстрее остальных —
`POST /orders/{id}/self-assign` (`user_id`, обязательная `reason`)
позволяет взять `pending`-заказ вне очереди, минуя обычный цикл
предложений.

- **Доступен только для `pending`-заказов** (`400` иначе) — самоназначиться
  на уже кому-то назначенный заказ бессмысленно, для этого есть обычный
  `/respond`
- **`reason` обязательна и не может быть пустой строкой/пробелами** —
  единственное место в проекте, где реализован паттерн
  "обязательное текстовое поле → сохраняется и видно в истории"
- **Сохраняется в двух местах:** `Order.self_assign_reason` (миграция
  `ed3788bb5a0a`) — показывается отдельной колонкой на странице «История
  заказов» (`static/history.html`/`history.js`), и в `ActivityLog.message`
  нового события `order_self_assigned` — видно на странице «Журнал
  действий». `Order.self_assign_reason` осознанно не переиспользует
  `OrderOffer` — у заказа может быть максимум одно самоназначение
  (терминальный переход в `assigned`), отдельная колонка проще, чем
  вытаскивать причину из последнего `OrderOffer`
- **Если у заказа была активная офера кому-то другому** — она помечается
  `declined` (не остаётся висеть `pending`), но позиция в очереди
  предложенного водителя не меняется — он ничего не терял, у него просто
  забрали заказ раньше, чем он успел ответить
- **Переход в очереди — тот же код, что в `respond_to_order` (ветка
  `accepted`)**: `max_position + 1`, тот же принцип, что и при обычном
  принятии — существующая логика распределения заказов по очереди не
  меняется (это явное требование в критериях приёмки issue)
- **Проверка, что `user_id` состоит в очереди этого же типа** (`QueuePosition`
  с нужным `queue_type` существует) — `400`, если нет. Это не про identity
  (см. технический долг ниже — тот же неаудируемый `user_id` из тела
  запроса, что и везде), а про то, что в `/users` есть и диспетчеры без
  очереди (см. `GET /users`), а с Шага 23 ещё и про то, что водитель может
  состоять только в одной из двух очередей; без этой проверки
  самоназначение уронило бы запрос `500`-й ошибкой на `user_qp.position`
- **VK-уведомление** — отдельная функция `notify_self_assigned`
  (`app/notifications.py`), не переиспользует `notify_accepted`, чтобы
  явно назвать это самоназначением вне очереди и включить причину в
  текст сообщения
- **Тот же identity-долг, что у `/respond`/`/complete`** (см. ниже) —
  `/self-assign` тоже не проверяет, что вызывающий действительно тот, за
  кого себя выдаёт; осознанно не стали делать исключение для нового
  эндпоинта, чтобы не плодить разные модели доступа

## Статистика (Шаг 22)

По GitHub issue: страница «Статистика» с общими счётчиками по заказам
и разбивкой по водителям, чтобы видеть общую картину и равномерность
распределения заказов. Issue написан задолго до текущего состояния
кода — часть формулировок в нём устарела:

- Issue помечает счётчик отменённых заказов как «если будет
  реализовано» — отмена (`OrderStatus.cancelled`, `/orders/{id}/cancel`)
  уже реализована, счётчик включён без условности
- Issue предлагает на будущее завести `OrderEvent` для истории событий
  заказа (отказы, переходы между водителями). Это уже есть —
  `ActivityLog`/`GET /activity` («Журнал действий», Шаг 19). Новую
  сущность заводить не нужно; статистика первой версии её не
  использует (см. ниже), но при будущем расширении (например, счётчик
  отказов по водителю) источник данных уже есть

**`GET /statistics/summary`** — единственный эндпоинт, один проход по
всем заказам (`select(Order)`, без пагинации — тот же довод, что уже
принят для `GET /orders`: масштаб ~10 человек/несколько сотен заказов
не требует SQL `GROUP BY`) даёт сразу оба блока ответа:

- `overall`: `total`/`completed`/`active`/`cancelled`. `active` —
  `pending` и `assigned` одним числом (issue описывает «активные заказы»
  одним пунктом, не двумя). Инвариант: `total == completed + active +
  cancelled`
- `by_driver`: только те, кто **сейчас** состоит хотя бы в одной из
  двух очередей (есть `QueuePosition`, независимо от `queue_type`) —
  не все `GET /users` целиком. Диспетчеры (`--no-queue`) никогда не
  получают заказы, их строки 0/0 были бы просто шумом. Запрос — `select(User)...distinct()`,
  не join через `QueuePosition` напрямую: с Шага 23 водитель может
  состоять в обеих очередях сразу (две строки `QueuePosition`), без
  `distinct()` он задваивался бы в таблице с одинаковыми числами —
  `received`/`completed`/`cancelled` считаются от `Order.assigned_to`,
  не от `QueuePosition`, так что дубль был бы неотличим от настоящей
  строки. Для каждого — `received`/`completed`/`cancelled`:
  - `received` — все заказы, когда-либо назначенные этому водителю
    (`Order.assigned_to`), независимо от текущего статуса
  - `completed`/`cancelled` — непересекающиеся подмножества `received`
    (третье возможное состояние внутри `received` — заказ ещё активен)
  - `cancel_order` не очищает `assigned_to` (см. выше) — отменённый
    после назначения заказ поэтому всё равно входит в `received`
    водителя (он его правда получил, просто не довёз), и отдельно
    учитывается в `cancelled`. Первая версия из issue предлагала для
    водителя только 2 колонки (получено/завершено); решили сразу
    добавить `cancelled` третьей колонкой, а не растворять отменённые
    заказы в `received` незаметно
  - сортировка — по убыванию `received`, как в примере таблицы в issue
- Самоназначение (`/self-assign`, Шаг 20) не требует отдельной
  обработки — оно пишет `Order.assigned_to` тем же полем, что обычное
  принятие, и попадает в счётчики автоматически
- Эндпоинт полностью read-only — ничего не пишет в БД, поэтому критерий
  приёмки «существующая логика очереди и распределения заказов не
  изменяется» выполняется по построению

**Фронтенд** (`static/statistics.html` + `statistics.js`) — по образцу
`history.html`/`history.js`: общая статистика — простой `<ul>` (в
проекте нет компонента «карточка», не заводили его ради 4 чисел),
статистика по водителям — таблица с тем же адаптивным CSS-паттерном,
что `#history-table` (переход в карточки на мобильном), но
**продублированным** под своим id (`#driver-stats-table`), а не
обобщённым в общий класс — стили таблиц/списков в проекте и так уже
привязаны к конкретной странице по id/классу (`.price-list`,
`.activity-list`, `#history-table`), решили не трогать уже работающую
страницу «История заказов» ради обобщения, которого не просили.

## Две очереди — дальние/короткие (Шаг 23)

До Шага 23 в проекте была одна очередь (де-факто дальние/межгородние
поездки). По запросу пользователя завели вторую, для коротких поездок,
полностью независимую от первой.

- **`QueueType` (`long`/`short`)** — `app/models/queue.py`, рядом с
  `QueuePosition` (не отдельный shared-модуль: `OrderStatus`/`OfferResponse`
  в проекте тоже живут рядом со своей главной моделью, а не в общем
  файле). `Order.queue_type` и `QueuePosition.queue_type` используют
  один и тот же enum
- **`QueuePosition` уникальна по паре `(user_id, queue_type)`**, не по
  одному `user_id` — водитель может состоять в обеих очередях
  одновременно, с независимыми позициями в каждой. Это единственное
  изменение модели данных, всё остальное — фильтрация существующих
  запросов
- **`Order.queue_type` обязателен, без значения по умолчанию** — ни на
  уровне API (`422`, если не передан), ни на уровне формы (радиокнопки
  «Дальний»/«Короткий» без предвыбора, `required`, дэшборд). Осознанно
  не стали автоопределять тип по тексту маршрута — свободный текст не
  даёт для этого надёжных данных, а угадывание там, где от этого
  зависит, какая очередь получит заказ, — плохая идея (см. также
  предупреждение о латинице в маршруте — там та же логика: авто-фикс
  неоднозначного случая не делаем, только явный сигнал)
- **Вся арифметика очереди фильтруется по `queue_type` заказа** — в
  `create_order` (кому предложить первым), в обеих ветках
  `respond_to_order` (перенос в конец / поиск следующего по кругу,
  включая разворот с последнего на первого), в `self_assign_order`
  (перенос в конец) и в `cancel_order` (переиндексация при возврате
  вторым местом). Самое чувствительное место — `cancel_order`: без
  фильтра переиндексация `position = 0, 1, 2, ...` при возврате
  водителя задела бы **обе** очереди разом, а не только ту, где произошла
  отмена
- **`GET /queue` — опциональный `queue_type`.** Без параметра отдаёт
  позиции из обеих очередей сразу (используется страницами, которым
  нужен просто список водителей, а не порядок конкретной очереди —
  `history.js`/`activity.js` дёргают `/queue` только ради имён для
  фильтра); с параметром — порядок одной конкретной очереди, для двух
  блоков на дэшборде. Без параметра водитель, состоящий в обеих
  очередях, приходит дважды — `populateUserFilter` в `history.js`/
  `activity.js` дедуплицирует по `user_id` на клиенте
- **Миграция БД (`5437dcec06ba`) — клонирование, не пустой старт.**
  Короткая очередь при вводе фичи заполняется тем же составом и тем же
  порядком, что текущая (единственная на тот момент) дальняя — дальше
  обе живут независимо. `scripts/add_user.py` продолжает эту логику:
  по умолчанию новый водитель ставится в конец **обеих** очередей
  (флаг `--queue-type=long|short` — только в одну, для водителя,
  который возит не всё). Технически первая миграция в проекте, где
  SQLite потребовал `batch_alter_table` (пересоздание таблицы) сразу на
  двух таблицах — смена `nullable` на `order.queue_type` и смена
  `UNIQUE(user_id)` на составной `UNIQUE(user_id, queue_type)` на
  `queueposition`. Исходный constraint оказался анонимным (создан без
  имени в самой первой миграции `4cc9dd7701d8`) — `drop_constraint`
  внутри batch-режима нашёл его только через явный `naming_convention`,
  подобранный под то, как Alembic называет анонимные constraint'ы при
  рефлексии
- **Что осталось единым, не разделено по очередям:** секции «Ожидают
  ответа» и «Мои заказы в пути» на дэшборде — один список каждая, тип
  заказа показан бейджем рядом с маршрутом, а не двумя параллельными
  подсписками (решение по итогам обсуждения — вдвое больше вёрстки и
  JS ради обычно 1-2 заказов одновременно того не стоило). «Статистика»
  тоже осталась общей (`by_driver` считает заказы обоих типов вместе) —
  не запрошено, разбивка по типу — возможное расширение на будущее,
  данные для него уже есть
- **VK-уведомления** (`app/notifications.py`) называют тип поездки в
  тексте сообщения — единственный канал, где иначе неоткуда узнать,
  о какой из двух очередей речь (в отличие от дэшборда/истории, где
  это видно из интерфейса)

## Архитектура фронтенда (Шаг 9)

- **Структура страниц:** дэшборд (очередь + индикатор активного предложения +
  форма создания заказа) на одной странице; история заказов — отдельная
  страница (таблица + фильтры `status`/`user_id`/`queue_type`, поверх `GET /orders`);
  журнал действий — отдельная страница (список + фильтры `user_id`/
  `event_type`, поверх `GET /activity`, см. «Журнал действий» выше)
- **"Кто я":** без полноценной авторизации. Селектор пользователя в шапке,
  выбор сохраняется в `localStorage`, дальше действия идут от выбранного
  `user_id` автоматически
- **Технология:** обычный HTML + vanilla JS, без шаблонизаторов. JS дёргает
  `fetch()` к готовому API, бэкенд почти не трогаем
- **Индикатор "кому сейчас предложен заказ"** — нужен явно в интерфейсе,
  не только через `/docs`

  cmd.exe, не PowerShell)
