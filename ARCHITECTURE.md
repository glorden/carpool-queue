# Архитектура и решения — Carpool Queue

Здесь фиксируем решения, которые живут дольше одного шага: логику,
которую нельзя менять не подумав, зафиксированный технический долг
и стек технологий. Хронология выполненных шагов — в [PROGRESS.md](./PROGRESS.md).

## Стек технологий

Ubuntu Server, Caddy, Python 3.13, FastAPI, SQLModel, SQLite, Alembic.
Приватный репозиторий: https://github.com/glorden/carpool-queue

## Логика очереди (ключевое бизнес-правило)

С Шага 23 в проекте две полностью независимые очереди — `QueueType.long`
(дальние/межгородние поездки) и `QueueType.short` (короткие). Один и тот
же водитель может состоять в обеих одновременно (`QueuePosition`
уникальна по паре `user_id`+`queue_type`, не по одному `user_id`).
Каждый `Order` обязан иметь `queue_type`, и вся арифметика ниже
применяется **только** к очереди этого типа — заказ дальней очереди
никогда не читает и не переставляет позиции в короткой, и наоборот.
Подробности — раздел «Две очереди» ниже.

- Заказ создаётся → сразу автоматически предлагается первому в очереди
  своего типа (создаётся `OrderOffer`)
- Принял → сразу уходит в конец очереди (не дожидаясь завершения поездки —
  иначе новый заказ мог бы снова прийти тому, кто уже занят)
- Выполнил поездку → отдельно помечается через `/complete` (статус, время)
- Отказался → остаётся на своей позиции, заказ автоматически уходит
  следующему по очереди (по кругу, если отказавшийся был последним)
- Самоназначился (`/self-assign`) на `pending`-заказ вне очереди (с
  обязательной причиной) → тот же переход, что при `accepted`: сразу
  становится исполнителем и уходит в конец очереди (`max + 1`).
  Существующая офера, если она была кому-то другому, помечается
  `declined`, чтобы не оставалась висеть — сам предложенный водитель
  свою позицию в очереди при этом не теряет
- Таймаутов на ответ нет — ждём сколько угодно, люди договариваются
  в личном чате
- Отменён (`/cancel`) → если заказ был `assigned`, водитель, взявший
  заказ, возвращается в начало очереди — но **вторым**, сразу после
  текущего первого, а не обгоняя его. Причина: если пассажир отказался
  не по вине водителя, тот не должен терять место из-за чужой отмены,
  но и не должен вытеснять того, кто честно ждёт своей очереди первым
  (проверено на реальном сценарии — см. PROGRESS.md, Шаг 13)

## Архитектурные решения и упрощения

- **`POST /orders` сразу создаёт `OrderOffer`** для первого в очереди —
  изначально планировалось отдельным шагом, но оказалось логичнее сразу:
  заказ без предложения кому-то не имеет смысла как отдельное состояние
- **`POST /orders/{id}/respond`** — с Шага 26 проверяет identity по
  сессии (оффер ищется строго по `current_user.id`, `403` иначе), с
  Шага 28 — ещё и роль `driver` (см. «Роли и права доступа»)
- **`POST /orders/{id}/complete`** — с Шага 26 проверяет, что
  `assigned_to` совпадает с вызывающим (`403` иначе), с Шага 28 — плюс
  роль `driver`
- **Ошибки — только через `HTTPException`**, не через `return {"error": ...}`.
  Причина: при `response_model=Order` FastAPI силой приводил словарь
  к модели, и сообщение об ошибке терялось (ответ превращался в "пустой"
  `Order` с `null`-полями). Теперь: `{"detail": "..."}` + корректный
  HTTP-статус (`404`/`400`)
- **`GET /orders` без пагинации** — только `limit` (default=100, max=500).
  При масштабе 10 человек / несколько сотен заказов offset/total считаем
  лишней сложностью
- **`GET /orders` не отдаёт `OrderOffer`** — плоский список `Order`,
  единообразно с `/respond` и `/complete`. Детальная история предложений —
  отдельный эндпоинт при необходимости (`GET /orders/{id}/offers`)
- **`POST /orders/{id}/cancel`** — отменяет заказ из `pending` или
  `assigned`; из `completed`/`cancelled` — `400`.
  Тела запроса не требует (как и `/complete`): для `assigned`-заказа
  водитель уже известен из `order.assigned_to`, идентичность
  вызывающего не проверяется — та же модель доступа, что у
  `/respond`/`/complete`. Возврат в очередь **вторым** (не первым)
  требует вставки между текущими 1-м и 2-м местом — тут, в отличие
  от ухода в конец при `accepted` (`max + 1`, коллизий не бывает),
  переиндексирует всю очередь (`position = 0, 1, 2, ...` в новом
  порядке), т.к. позиции не гарантированно идут подряд без пропусков

## Технический долг — закрыт (Шаг 26)

До Шага 26 `/respond`, `/self-assign`, `/complete`, `/cancel` и
`POST/PUT/DELETE /price` принимали `user_id` в теле запроса и никак не
проверяли, что вызывающий — это правда он. Шаг 25 дал источник identity
(серверная сессия после входа через VK ID), Шаг 26 — реальные проверки
на всех перечисленных эндпоинтах. `user_id` убран из тел запросов/query-
параметров полностью (не остался как игнорируемое поле).

- `get_current_user_required` (`app/auth.py`) — строгий вариант поверх
  `get_current_user_optional`, `401` без сессии
- `/respond`: `OrderOffer` фильтруется сразу по `user_id ==
  current_user.id` + `pending`; `403`, если оффера для текущего
  пользователя нет
- `/self-assign`: identity из `current_user.id`
- `/complete`: `403`, если `order.assigned_to != current_user.id`
- `/orders` (создание): требует сессию, `Order.created_by =
  current_user.id` — новое nullable-поле (миграция `90893e2b4590`,
  `batch_alter_table` — на SQLite новый foreign key не добавить вне
  batch-режима), nullable навсегда: заказы, созданные до Шага 26, не
  заполнить задним числом (тот же принцип, что и `assigned_to`/
  `self_assign_reason`)
- `/cancel`: для `pending` — `403`, если `order.created_by` задан и не
  совпадает с вызывающим; для `assigned` — разрешён и создателю, и
  исполнителю (оба варианта), `403` третьим лицам. Если `created_by is
  None` (исторический заказ до миграции) — разрешено любому
  залогиненному, иначе такой заказ вообще нельзя было бы отменить
  никому
- `POST/PUT/DELETE /price`: `PriceLogEntry.user_id` — из сессии, не из
  тела. Сверки "своя/чужая" позиция сознательно нет — прайс остаётся
  коллективным (см. «Редактирование прайса», Шаг 12), поменялся только
  источник `user_id` в логе, не модель доступа
- Тестовая инфраструктура: `tests/conftest.py` → `login_as(engine,
  user_id)` переопределяет `get_current_user_required`/
  `_optional` через `app.dependency_overrides` (тем же приёмом, что уже
  использовался для `get_session`) — тесты действуют от имени
  конкретного пользователя без реального похода в VK. `tests/
  test_authorization.py` — 401/403-сценарии по каждому эндпоинту

**Наглядная деталь логики очереди, всплывшая при написании тестов:**
оффер на `pending`-заказ уходит первому в очереди, а не тому, кто заказ
создал — если создатель сам первый в очереди (частый случай в тестах
через `seed_queue`), `created_by` и `assigned_to` совпадают, и разница
между ролями не проверяется. Чтобы реально развести роли "создатель" и
"исполнитель" (в тестах и при ручной проверке), создавать заказ должен
не первый в очереди человек.

## Технический долг — закрыт (Шаг 27)

Шаг 26 закрыл identity-проверки на мутирующих эндпоинтах, но
GET-эндпоинты списков (`/users`, `/queue`, `/orders`, `/orders/pending`,
`/price`, `/price/log`, `/activity`, `/statistics/summary`) оставались
без проверки сессии на уровне приложения — держались только на внешнем
HTTP Basic Auth в Caddy (см. «Вход через VK ID» выше). Шаг 27 закрывает
этот последний пробел и одновременно убирает сам Caddy Basic Auth — VK-
сессия становится единственной защитой сайта, не второй рядом с паролем.

- Все 8 перечисленных эндпоинтов получили `Depends(get_current_user_required)`
  — тот же паттерн, что уже применялся на мутирующих эндпоинтах в Шаге 26,
  без нового механизма (явный `Depends` в каждом хендлере, не общий
  middleware — решение по итогам обсуждения: `tests/conftest.py::login_as()`
  переопределяет `get_current_user_required` через `app.dependency_overrides`,
  то есть работает на уровне FastAPI DI; middleware читал бы `request.session`
  в обход DI и потребовал бы отдельного механизма логина тестового клиента).
  Ответ не меняется для залогиненных, `401` для остальных
- `/docs`, `/redoc`, `/openapi.json` — тоже закрыты сессией, не отключены
  насовсем: `docs_url=None`/`redoc_url=None`/`openapi_url=None` в
  конструкторе `FastAPI(...)`, ручные роуты `GET /docs`/`/redoc`/
  `/openapi.json` поверх `Depends(get_current_user_required)`
  (официальный рецепт FastAPI для защиты docs). Причина не отключать —
  `/docs` реально используется в рабочем процессе (см. PROGRESS.md,
  многократные упоминания «проверено через /docs»); заводить отдельное
  `ENV`/`DEBUG`-разделение конфига специально ради этого было бы лишней
  инфраструктурой для 10 пользователей (в проекте такого разделения нет
  и не планировалось)
- **Фронтенд:** паттерн `#auth-gated`/`#login-prompt`, реализованный на
  дэшборде в Шаге 25 (см. выше), скопирован на `price.html`/
  `history.html`/`activity.html`/`statistics.html` — без сессии эти
  страницы показывают только приглашение войти и не делают ни одного
  запроса к данным (как и дэшборд). Без этой фронтенд-половины один
  только бэкенд-гейт превратил бы страницы в зависшую «Загрузка...» с
  необработанным `TypeError` в консоли (`fetch` вернул бы `{"detail":
  "Not authenticated"}` вместо массива) — обе половины обязательны вместе
- **Caddy Basic Auth убран целиком** (`/etc/caddy/Caddyfile` — один
  `reverse_proxy 127.0.0.1:8000` на весь домен, без `basic_auth` и без
  специального `handle /auth/vk/*`, который был нужен только чтобы
  обойти пароль для VK-callback — см. DEPLOY.md). VK-сессия — теперь
  единственный слой защиты сайта
- **Стоит держать в уме:** после снятия Caddy самопривязка VK-аккаунта
  (`/auth/vk/callback` → экран выбора себя из списка непривязанных
  `User`, см. «Вход через VK ID» выше) доступна буквально любому
  человеку в интернете, не только тому, кто прошёл Caddy-пароль. Риск
  не новый (сам `/auth/vk/*` был публичным уже с Шага 25), но раньше до
  самой кнопки входа ещё нужно было дойти через пароль. Если в базе
  остаются пользователи без привязанного `vk_id` на момент отключения
  Caddy — теоретически их может занять кто угодно первым; стоит
  проверить перед отключением, что свободных слотов не осталось
- Тесты: `tests/test_authorization.py` →
  `test_read_endpoints_require_session` (401 без сессии на все 8
  эндпоинтов), `tests/test_statistics.py` →
  `test_by_driver_excludes_users_without_queue_position` дополнен
  `login_as(...)` (единственный существующий тест, где один из восьми
  эндпоинтов вызывался без него). Итого 50 тестов, все зелёные

## Разделение бизнес-логики и FastAPI (задел на будущее, только на бумаге)

Сейчас весь роутинг живёт в одном `app/main.py` (без `APIRouter`), а бизнес-логика
(машина состояний заказа, математика очереди, вызовы уведомлений) написана прямо
в теле хендлеров — например, `respond_to_order` и `cancel_order`. Единственное, что
уже вынесено отдельно — `app/notifications.py`. Ничего из нижеперечисленного не
реализовано и не запланировано отдельным шагом — просто фиксируем целевую структуру
на случай, когда `main.py` разрастётся дальше, чтобы новая логика с этого момента
писалась сразу в правильном месте, а не переносилась потом целиком.

- **Роутеры — это двери в систему, сервисы — сама система.** Сегодня единственная
  дверь — REST API, но со временем могут появиться другие (Telegram-бот,
  HTML-интерфейс сверх текущего, импорт из файла, интеграция с другим сервисом).
  Все они должны вызывать одни и те же методы `services`, а правила работы очереди
  и заказов — оставаться в одном месте независимо от числа дверей
- **`app/routers/*.py`** — по файлу на ресурс (`orders.py`, `queue.py`, `price.py`),
  через `APIRouter` + `include_router` в `main.py`. Чисто транспорт: разобрал вход →
  вызвал сервис → вернул ответ; `HTTPException` на валидации входа может подниматься
  и здесь
- **`app/services/*.py`** — по файлу на домен (`orders.py`, `queue.py`), функции вида
  `respond_to_order(session, order_id, user_id, response) -> Order`. Вся машина
  состояний заказа и математика очереди — здесь, не в роутере
- **Правило на будущее, а не разовая задача:** новый или изменяемый эндпоинт, где
  логика выходит за пару строк, сразу пишется как тонкий `router` + `service`-функция
- **Побочный эффект:** такие `service`-функции можно будет тестировать напрямую, без
  `TestClient`/HTTP — закроет сегодняшний пробел, где `tests/test_queue_logic.py`
  может дойти до логики очереди только через HTTP
- **Осознанно не заводим** repository-слой, DI-контейнер или иерархию кастомных
  исключений — для масштаба 10 доверенных пользователей это была бы лишняя
  сложность; `HTTPException` из сервиса — этого достаточно

## Редактирование прайса (Шаг 12)

`/price` (`POST`/`PUT`/`DELETE`) сознательно сделаны по той же модели
доступа, что и `/respond`/`/complete`: любой `user_id` может добавить,
изменить или удалить любую позицию прайса, без проверки, что это
"его" изменение. Причина та же — доверенная группа ~10 человек, а
не случайные пользователи (доступ ко всему сайту в любом случае
закрыт VK ID, см. «Вход через VK ID» и «Технический долг — закрыт
(Шаг 27)» ниже).

Компенсация риска — не запрет, а прозрачность: каждое изменение пишет
запись в `PriceLogEntry` (кто/когда/что — `old_value`/`new_value`
снэпшотами), лог виден прямо на странице «Прайс» (`GET /price/log`).
Если кто-то ошибётся или удалит не то — видно, кто и когда, откатывать
приходится вручную (отдельного undo нет — сочли лишним для этого
масштаба).

## Уведомления водителям (Шаг 14)

Когда заказ создаётся или переходит следующему по очереди (тот же
момент, когда создаётся `OrderOffer`), бэкенд шлёт сообщение в общую
беседу VK, где состоят все водители — "Заказ #12 (маршрут) предложен:
Имя".

- **Канал — VK, а не Telegram/Web Push**: у группы уже есть общая
  беседа VK, где все состоят, — это единственный канал без email/SMS
  и без личных чатов по отдельности. Сообщество добавлено в беседу
  как обычный участник (одноразовая настройка вручную), пишет через
  `messages.send` с токеном сообщества (`VK_GROUP_TOKEN`) в
  `VK_PEER_ID` (id беседы)
- **Тег водителя в сообщении** — `User.vk_id` (nullable, миграция
  `296fad1e2c65`) хранит VK id водителя. Если он известен — сообщение
  тегает его (`[id...|Имя]`), иначе просто пишет имя текстом (без
  vk_id код продолжает работать как раньше). Заполняется вручную
  (сопоставление по имени между участниками беседы и `User.name`,
  бэкофисной формы для этого нет — редкая разовая операция)
- **Ссылка на сайт** в каждом сообщении (`SITE_URL` в `.env`, по
  умолчанию `https://zakaz.glorden.ru/`) — учти, что сайт закрыт
  VK ID (см. «Технический долг — закрыт (Шаг 27)» ниже): по ссылке без
  сессии откроется только приглашение войти, не сами данные
- **Best-effort, не блокирует заказ** — `app/notifications.py:notify_offer`
  оборачивает вызов VK API в `try/except`, любая ошибка (нет токена,
  таймаут, VK API вернул ошибку) только логируется, само создание/
  переход заказа не откатывается и не падает
- **Конфигурация — только через `.env`** (`VK_GROUP_TOKEN`,
  `VK_PEER_ID`), оба значения опциональны: без них уведомления просто
  не отправляются, остальной сервис работает как обычно

## Бэкап базы данных (Шаг 15)

Единственный `carpool.db` на VPS — риск потери данных при случайном
удалении (например, через `/price`) или сбое диска. Решение: ежедневный
`sqlite3 .backup` через cron (`scripts/backup_db.sh`), без внешнего
хранилища — принимаем риск полной потери VPS как маловероятный для
этого масштаба.

Хранение — не просто "последние N дней", а гибрид:
- самая свежая копия хранится всегда, сколько бы времени ни прошло;
- более старые копии переживают ежедневную чистку только по сетке
  "раз в 10 дней", отсчитанной от фиксированной даты (`EPOCH` в
  скрипте) — так со временем остаются срезы за все периоды жизни
  проекта, а не только за последний месяц, и место не растёт
  бесконечно (после года — 36 файлов, а не 365)

Восстановление — вручную (см. DEPLOY.md), автоматического failover нет.

## Журнал действий (Шаг 19)

Отдельная сущность `ActivityLog` (`app/models/activity.py`), не заменяет
историю заказов (`Order`) — дополняет её хронологией событий по ходу
жизни заказа и очереди, по образцу `GET /issues` из GitHub-заявки на
эту фичу. Поля: `id`, `created_at`, `user_id` (nullable), `order_id`
(nullable), `event_type`, `message` (готовый текст для UI, не собирается
из шаблона на фронте).

- **Пишется из `app/main.py` напрямую в тех же хендлерах**, что и
  сами переходы заказа (`create_order`, `respond_to_order`,
  `complete_order`, `cancel_order`) — тем же способом, что `PriceLogEntry`
  в `/price`. Отдельного router/service под это не заводили — см. «Разделение
  бизнес-логики и FastAPI» выше, туда же попадёт при рефакторинге, если
  дойдёт до него
- **`event_type` значения:** `order_created`, `order_offered`,
  `order_accepted`, `order_declined`, `order_completed`, `order_cancelled`,
  `queue_changed` (используется дважды — уход в конец очереди при
  принятии и возврат в начало при отмене назначенного заказа)
- **`user_id` не всегда известен.** У `POST /orders`, `/complete` и
  `/cancel` нет тела запроса с id исполнителя (тот же identity-долг,
  что описан выше) — событие в этих случаях пишется с `user_id=None`,
  но с осмысленным текстом в `message`
- **`GET /activity`** — фильтры `user_id`/`order_id`/`event_type`,
  `limit` (default=100, max=500), новые сверху. Реализация — копия
  паттерна `GET /price/log`
- **Побочный баг, найденный при реализации:** запись лога сразу после
  `session.commit()` инвалидирует (`expire`) уже загруженный ORM-объект;
  если его потом вернуть как `response_model` без повторного `refresh`,
  FastAPI молча сериализует пустой `{}` вместо реальных полей (без
  ошибки, без 500). Тот же баг уже существовал в `POST/PUT /price` —
  просто был незаметен, потому что фронтенд не читает поля из ответа
  этих ручек. Исправлено добавлением `session.refresh(...)` после
  каждого коммита лога, перед `return`. Если добавляешь новый
  `_log_activity`/`PriceLogEntry`-подобный вызов после того, как объект
  уже был зарефрешен — не забудь зарефрешить его снова перед возвратом

## Самоназначение на заказ (Шаг 20)

По GitHub issue: иногда водитель уже находится в городе подачи или по
другой уважительной причине может выполнить заказ быстрее остальных —
`POST /orders/{id}/self-assign` (`user_id`, обязательная `reason`)
позволяет взять `pending`-заказ вне очереди, минуя обычный цикл
предложений.

- **Доступен только для `pending`-заказов** (`400` иначе) — самоназначиться
  на уже кому-то назначенный заказ бессмысленно, для этого есть обычный
  `/respond`
- **`reason` обязательна и не может быть пустой строкой/пробелами** —
  единственное место в проекте, где реализован паттерн
  "обязательное текстовое поле → сохраняется и видно в истории"
- **Сохраняется в двух местах:** `Order.self_assign_reason` (миграция
  `ed3788bb5a0a`) — показывается отдельной колонкой на странице «История
  заказов» (`static/history.html`/`history.js`), и в `ActivityLog.message`
  нового события `order_self_assigned` — видно на странице «Журнал
  действий». `Order.self_assign_reason` осознанно не переиспользует
  `OrderOffer` — у заказа может быть максимум одно самоназначение
  (терминальный переход в `assigned`), отдельная колонка проще, чем
  вытаскивать причину из последнего `OrderOffer`
- **Если у заказа была активная офера кому-то другому** — она помечается
  `declined` (не остаётся висеть `pending`), но позиция в очереди
  предложенного водителя не меняется — он ничего не терял, у него просто
  забрали заказ раньше, чем он успел ответить
- **Переход в очереди — тот же код, что в `respond_to_order` (ветка
  `accepted`)**: `max_position + 1`, тот же принцип, что и при обычном
  принятии — существующая логика распределения заказов по очереди не
  меняется (это явное требование в критериях приёмки issue)
- **Проверка, что `user_id` состоит в очереди этого же типа** (`QueuePosition`
  с нужным `queue_type` существует) — `400`, если нет. Это бизнес-правило
  поверх ролевого гейта `require_driver` (Шаг 28, см. «Роли и права
  доступа») — роль решает «вообще можно самоназначаться», эта проверка —
  «можно именно в этой очереди»; с Шага 23 ещё и про то, что водитель
  может состоять только в одной из двух очередей. Без неё самоназначение
  уронило бы запрос `500`-й ошибкой на `user_qp.position`
- **VK-уведомление** — отдельная функция `notify_self_assigned`
  (`app/notifications.py`), не переиспользует `notify_accepted`, чтобы
  явно назвать это самоназначением вне очереди и включить причину в
  текст сообщения
- **Та же модель доступа, что у `/respond`/`/complete`** — идентичность
  из сессии (Шаг 26), роль `driver` поверх (Шаг 28); осознанно не стали
  делать исключение для этого эндпоинта, чтобы не плодить разные модели
  доступа

## Статистика (Шаг 22)

По GitHub issue: страница «Статистика» с общими счётчиками по заказам
и разбивкой по водителям, чтобы видеть общую картину и равномерность
распределения заказов. Issue написан задолго до текущего состояния
кода — часть формулировок в нём устарела:

- Issue помечает счётчик отменённых заказов как «если будет
  реализовано» — отмена (`OrderStatus.cancelled`, `/orders/{id}/cancel`)
  уже реализована, счётчик включён без условности
- Issue предлагает на будущее завести `OrderEvent` для истории событий
  заказа (отказы, переходы между водителями). Это уже есть —
  `ActivityLog`/`GET /activity` («Журнал действий», Шаг 19). Новую
  сущность заводить не нужно; статистика первой версии её не
  использует (см. ниже), но при будущем расширении (например, счётчик
  отказов по водителю) источник данных уже есть

**`GET /statistics/summary`** — единственный эндпоинт, один проход по
всем заказам (`select(Order)`, без пагинации — тот же довод, что уже
принят для `GET /orders`: масштаб ~10 человек/несколько сотен заказов
не требует SQL `GROUP BY`) даёт сразу оба блока ответа:

- `overall`: `total`/`completed`/`active`/`cancelled`. `active` —
  `pending` и `assigned` одним числом (issue описывает «активные заказы»
  одним пунктом, не двумя). Инвариант: `total == completed + active +
  cancelled`
- `by_driver`: только те, кто **сейчас** состоит хотя бы в одной из
  двух очередей (есть `QueuePosition`, независимо от `queue_type`) —
  не все `GET /users` целиком. Диспетчеры (`--no-queue`) никогда не
  получают заказы, их строки 0/0 были бы просто шумом. Запрос — `select(User)...distinct()`,
  не join через `QueuePosition` напрямую: с Шага 23 водитель может
  состоять в обеих очередях сразу (две строки `QueuePosition`), без
  `distinct()` он задваивался бы в таблице с одинаковыми числами —
  `received`/`completed`/`cancelled` считаются от `Order.assigned_to`,
  не от `QueuePosition`, так что дубль был бы неотличим от настоящей
  строки. Для каждого — `received`/`completed`/`cancelled`:
  - `received` — все заказы, когда-либо назначенные этому водителю
    (`Order.assigned_to`), независимо от текущего статуса
  - `completed`/`cancelled` — непересекающиеся подмножества `received`
    (третье возможное состояние внутри `received` — заказ ещё активен)
  - `cancel_order` не очищает `assigned_to` (см. выше) — отменённый
    после назначения заказ поэтому всё равно входит в `received`
    водителя (он его правда получил, просто не довёз), и отдельно
    учитывается в `cancelled`. Первая версия из issue предлагала для
    водителя только 2 колонки (получено/завершено); решили сразу
    добавить `cancelled` третьей колонкой, а не растворять отменённые
    заказы в `received` незаметно
  - сортировка — по убыванию `received`, как в примере таблицы в issue
- Самоназначение (`/self-assign`, Шаг 20) не требует отдельной
  обработки — оно пишет `Order.assigned_to` тем же полем, что обычное
  принятие, и попадает в счётчики автоматически
- Эндпоинт полностью read-only — ничего не пишет в БД, поэтому критерий
  приёмки «существующая логика очереди и распределения заказов не
  изменяется» выполняется по построению

**Фронтенд** (`static/statistics.html` + `statistics.js`) — по образцу
`history.html`/`history.js`: общая статистика — простой `<ul>` (в
проекте нет компонента «карточка», не заводили его ради 4 чисел),
статистика по водителям — таблица с тем же адаптивным CSS-паттерном,
что `#history-table` (переход в карточки на мобильном), но
**продублированным** под своим id (`#driver-stats-table`), а не
обобщённым в общий класс — стили таблиц/списков в проекте и так уже
привязаны к конкретной странице по id/классу (`.price-list`,
`.activity-list`, `#history-table`), решили не трогать уже работающую
страницу «История заказов» ради обобщения, которого не просили.

## Две очереди — дальние/короткие (Шаг 23)

До Шага 23 в проекте была одна очередь (де-факто дальние/межгородние
поездки). По запросу пользователя завели вторую, для коротких поездок,
полностью независимую от первой.

- **`QueueType` (`long`/`short`)** — `app/models/queue.py`, рядом с
  `QueuePosition` (не отдельный shared-модуль: `OrderStatus`/`OfferResponse`
  в проекте тоже живут рядом со своей главной моделью, а не в общем
  файле). `Order.queue_type` и `QueuePosition.queue_type` используют
  один и тот же enum
- **`QueuePosition` уникальна по паре `(user_id, queue_type)`**, не по
  одному `user_id` — водитель может состоять в обеих очередях
  одновременно, с независимыми позициями в каждой. Это единственное
  изменение модели данных, всё остальное — фильтрация существующих
  запросов
- **`Order.queue_type` обязателен, без значения по умолчанию** — ни на
  уровне API (`422`, если не передан), ни на уровне формы (радиокнопки
  «Дальний»/«Короткий» без предвыбора, `required`, дэшборд). Осознанно
  не стали автоопределять тип по тексту маршрута — свободный текст не
  даёт для этого надёжных данных, а угадывание там, где от этого
  зависит, какая очередь получит заказ, — плохая идея (см. также
  предупреждение о латинице в маршруте — там та же логика: авто-фикс
  неоднозначного случая не делаем, только явный сигнал)
- **Вся арифметика очереди фильтруется по `queue_type` заказа** — в
  `create_order` (кому предложить первым), в обеих ветках
  `respond_to_order` (перенос в конец / поиск следующего по кругу,
  включая разворот с последнего на первого), в `self_assign_order`
  (перенос в конец) и в `cancel_order` (переиндексация при возврате
  вторым местом). Самое чувствительное место — `cancel_order`: без
  фильтра переиндексация `position = 0, 1, 2, ...` при возврате
  водителя задела бы **обе** очереди разом, а не только ту, где произошла
  отмена
- **`GET /queue` — опциональный `queue_type`.** Без параметра отдаёт
  позиции из обеих очередей сразу (используется страницами, которым
  нужен просто список водителей, а не порядок конкретной очереди —
  `history.js`/`activity.js` дёргают `/queue` только ради имён для
  фильтра); с параметром — порядок одной конкретной очереди, для двух
  блоков на дэшборде. Без параметра водитель, состоящий в обеих
  очередях, приходит дважды — `populateUserFilter` в `history.js`/
  `activity.js` дедуплицирует по `user_id` на клиенте
- **Миграция БД (`5437dcec06ba`) — клонирование, не пустой старт.**
  Короткая очередь при вводе фичи заполняется тем же составом и тем же
  порядком, что текущая (единственная на тот момент) дальняя — дальше
  обе живут независимо. `scripts/add_user.py` продолжает эту логику:
  по умолчанию новый водитель ставится в конец **обеих** очередей
  (флаг `--queue-type=long|short` — только в одну, для водителя,
  который возит не всё). Технически первая миграция в проекте, где
  SQLite потребовал `batch_alter_table` (пересоздание таблицы) сразу на
  двух таблицах — смена `nullable` на `order.queue_type` и смена
  `UNIQUE(user_id)` на составной `UNIQUE(user_id, queue_type)` на
  `queueposition`. Исходный constraint оказался анонимным (создан без
  имени в самой первой миграции `4cc9dd7701d8`) — `drop_constraint`
  внутри batch-режима нашёл его только через явный `naming_convention`,
  подобранный под то, как Alembic называет анонимные constraint'ы при
  рефлексии
- **Что осталось единым, не разделено по очередям:** секции «Ожидают
  ответа» и «Мои заказы в пути» на дэшборде — один список каждая, тип
  заказа показан бейджем рядом с маршрутом, а не двумя параллельными
  подсписками (решение по итогам обсуждения — вдвое больше вёрстки и
  JS ради обычно 1-2 заказов одновременно того не стоило). «Статистика»
  тоже осталась общей (`by_driver` считает заказы обоих типов вместе) —
  не запрошено, разбивка по типу — возможное расширение на будущее,
  данные для него уже есть
- **VK-уведомления** (`app/notifications.py`) называют тип поездки в
  тексте сообщения — единственный канал, где иначе неоткуда узнать,
  о какой из двух очередей речь (в отличие от дэшборда/истории, где
  это видно из интерфейса)

## Архитектура фронтенда (Шаг 9)

- **Структура страниц:** дэшборд (очередь + индикатор активного предложения +
  форма создания заказа) на одной странице; история заказов — отдельная
  страница (таблица + фильтры `status`/`user_id`/`queue_type`, поверх `GET /orders`);
  журнал действий — отдельная страница (список + фильтры `user_id`/
  `event_type`, поверх `GET /activity`, см. «Журнал действий» выше)
- **"Кто я":** без полноценной авторизации. Селектор пользователя в шапке,

  `user_id` автоматически
- **Технология:** обычный HTML + vanilla JS, без шаблонизаторов. JS дёргает
  `fetch()` к готовому API, бэкенд почти не трогаем
- **Индикатор "кому сейчас предложен заказ"** — нужен явно в интерфейсе,
  не только через `/docs`

## Вход через VK ID (Шаг 25)

До этого шага "кто я" был `<select>` в шапке дэшборда, выбор в
`localStorage`, без какой-либо серверной проверки (см. «Архитектура
фронтенда» выше). Шаг 25 заменяет это на вход через VK ID (VK OAuth) —
серверную сессию, привязанную к `User` через `vk_id`. Это первая часть
устранения identity-техдолга (см. выше): сам механизм получения текущего
пользователя. Вторая часть — реальные проверки на защищённых
эндпоинтах — отдельный, ещё не сделанный Шаг 26.

- **Сессия — `starlette.middleware.sessions.SessionMiddleware`**, не
  своя таблица в БД и не JWT. Подписанный (не зашифрованный) cookie на
  основе `itsdangerous`, весь контент сессии лежит в самом cookie.
  `SECRET_KEY` в `app/config.py` (был зарезервирован с самого начала
  проекта, нигде не использовался) — теперь ключ подписи. Для 10
  доверенных пользователей отдельное хранилище сессий или JWT решали бы
  несуществующую проблему (JWT нужен для нескольких независимых
  бэкендов — здесь один монолит)
- **`same_site="lax"`** — не дефолт по умолчанию, а сознательная защита:
  с появлением cookie-сессии кросс-сайтовые POST становятся CSRF-риском;
  `Lax` не прикрепляет cookie к межсайтовым POST/fetch, но прикрепляет
  к обычной top-level навигации — а именно так браузер возвращается с
  `id.vk.com` на `redirect_uri`. Отдельный CSRF-токен для существующих
  POST/PUT/DELETE эндпоинтов поэтому не понадобился
- **`https_only` управляется `SESSION_COOKIE_SECURE`** (`.env`, по
  умолчанию `true`) — на проде трафик снаружи всегда HTTPS (Caddy). При
  проверке в тестах выяснилось, что `Secure`-cookie не возвращается
  клиентом на `http://`-origin (даже на `testserver`/`127.0.0.1`) — это
  же стоит держать в уме при локальной отладке реального OAuth-похода
  через браузер, не только в `pytest` (`tests/conftest.py` использует
  `TestClient(app, base_url="https://testserver")` именно поэтому)
- **`code_verifier`/`state` (PKCE) — в той же сессионной cookie**, не в
  отдельном хранилище. Сессия работает и для ещё не залогиненного
  посетителя — значения кладутся в `request.session` перед редиректом на
  VK, читаются и удаляются в `/auth/vk/callback`. Модель угрозы PKCE
  (третья сторона перехватывает `code` без `verifier`) не ослабляется
  тем, что оба значения лежат в одном браузерном cookie легитимного
  пользователя
- **Привязка VK ↔ `User` — самопривязка при первом входе, не заранее
  вручную.** Новый `vk_id` (ещё ни у кого не занят) → если есть хотя бы
  один `User` без `vk_id` — экран `static/link-account.html` со списком
  таких `User`, выбор сохраняет `vk_id` навсегда; если свободных `User`
  нет — отказ (`static/login-denied.html`), новый `User` самостоятельно
  не создаётся (группа закрытая). Уже привязанный `vk_id` — сразу сессия,
  без экрана выбора. `User.vk_id` (был nullable, только для тега в VK-
  уведомлениях — см. «Уведомления водителям» ниже) стал `unique=True`:
  без этого ограничения гонка из двух вкладок на экране самопривязки
  могла бы привязать один VK-аккаунт к двум `User`; `IntegrityError` при
  коллизии превращается в `409` в `/auth/vk/link`
- **`password_hash` удалено из `User` целиком** (вместе с зависимостью
  `passlib[bcrypt]`) — поле было мертво уже до этого шага: нигде не
  проверялось, `scripts/add_user.py`/`scripts/seed.py` всегда писали туда
  заглушку. Оставлять неиспользуемое поле "пароль" в момент, когда
  описывается настоящий вход, — незаконченная работа, не осторожность
  (тот же принцип, что и с мёртвым статусом `unassigned`, см.
  CHANGELOG.md 0.2.0)
- **Миграция `6c16a556405e`** — `unique` на `vk_id` и `drop_column` на
  `password_hash`, обе операции на `user` в одном `batch_alter_table`
  (SQLite требует пересоздания таблицы для смены constraint'ов — та же
  причина, что и в `5437dcec06ba`, Шаг 23). Автогенерация заодно
  предложила `alter_column` на `order.status` (VARCHAR→Enum) — ложное
  срабатывание из-за того, что SQLite хранит `Enum` как VARCHAR без
  нативного типа, убрано вручную, к этой миграции не относится
- **`app/vk_oauth.py` — самодостаточный модуль**, сознательно не
  импортирует ничего из `app.database`/`app.models`/сессий/FastAPI,
  только сам протокол VK ID (PKCE, сборка URL, обмен кода на токен,
  парсинг ответа). Решение по итогам обсуждения: второго проекта,
  которому нужен VK-логин, сейчас нет, поэтому отдельный
  репозиторий/пакет заводить не стали — это была бы инфраструктура ради
  гипотетического будущего. Но если такой проект появится, этот файл
  можно будет просто скопировать почти без переделки (единственная
  зависимость от проекта — прямой импорт `app.config`, который в этом
  случае надо будет заменить параметрами функций)
- **Домен API — `id.vk.ru`, не `id.vk.com`.** Изначально код был написан
  на `id.vk.com` (сайт был недоступен для прямой проверки на этапе
  планирования), но `id.vk.com` вообще недоступен из части сетей —
  официальная документация обнаружилась на `id.vk.ru`, оттуда же
  подтверждены пути (`/authorize`, `/oauth2/auth`) и форма ответа обмена
  токена. Оба ранее открытых вопроса подтверждены по факту на живом
  трафике: `client_secret` передаётся в теле запроса (не в заголовке
  `Authorization`), и **отдельного вызова `/oauth2/user_info` в итоге
  нет** — официальная схема «без SDK, обмен на бэкенде» отдаёт `user_id`
  прямо в ответе `exchange_code()` (диаграмма и пример ответа в
  документации VK, не по аналогии со старым VK API, как предполагалось
  изначально). `app/vk_oauth.py` больше не содержит пометок `# СВЕРИТЬ` —
  всё подтверждено
- **Прямая работа с API без JS SDK — официально поддерживаемый VK путь**,
  не обходной. Теряются только "элементы быстрого входа" (One Tap,
  шторка), которые всё равно не планировались (см. выше, почему SDK не
  используется)
- **Официальный VK ID JS SDK сознательно не используется** —
  `client_secret` всё равно должен жить на сервере, обмен кода на токен
  идёт из бэкенда; чистый `<a href="/auth/vk/login">` проще и не тянет
  сторонний скрипт (проект до этого шага не подключал внешних скриптов
  вообще)
- **Фронтенд**: `static/js/session.js` — общий виджет "кто я" на всех
  страницах (по образцу `nav.js` — самостоятельно инициализируется при
  загрузке), результат — в `window.sessionReady` (promise), чтобы
  `dashboard.js`/`price.js` могли дождаться `currentUser` для своей
  инициализации без повторного запроса к `/me`. Виджет — общий элемент
  каркаса страницы (как `<nav>`), не часть `<header>` конкретной
  страницы (см. `STYLEGUIDE.md`)
- **На дэшборде без сессии не виден вообще никакой контент** —
  вся разметка (`#queue-section` в том числе) обёрнута в единый `#auth-
  gated`, скрытый без входа; вместо него — заметная заглушка
  (`#login-prompt`) с собственной крупной кнопкой "Войти через VK", не
  только маленькой в шапке. `dashboard.js` при отсутствии `currentUser`
  не делает вообще никаких запросов к `/queue`/`/orders/pending`/
  `/orders` — не только визуально скрывает, но и не тратит запросы
  впустую. Решение по итогам обсуждения: изначально (первая версия
  Шага 25) очередь оставалась видна всем без входа как "просмотр, не
  действие" — пересмотрено сразу после первого реального теста входа,
  когда стало ясно, что общий Basic Auth пароль (см. ниже) уже даёт
  доступ ко всем 10 людям без разбора, и видеть данные вообще без
  VK-входа избыточно
- **Важная оговорка (актуальна для Шагов 25-26, закрыта Шагом 27): это
  только UI-слой.** Сами эндпоинты (`GET /queue`, `GET /orders/pending`
  и т.п.) не проверяют сессию — данные всё ещё доступны прямым запросом
  к API в обход интерфейса (защищены только общим Basic Auth на Caddy,
  не VK-сессией). Реальная защита на уровне бэкенда — Шаг 26 закрывал
  только мутирующие эндпоинты, это упрощение сознательно не расширялось
  на `GET`-эндпоинты списков вплоть до Шага 27 (см. «Технический долг —
  закрыт (Шаг 27)» ниже), который закрывает и их, и убирает сам Caddy
  Basic Auth целиком
- **Что Шаг 25 сознательно не меняет:** контракт защищённых эндпоинтов
  (`/respond`, `/complete`, `/cancel`, `/price`) — тела запросов всё ещё
  принимают `user_id`, бэкенд его всё ещё не проверяет. Фронтенд просто
  подставляет туда `currentUser.user_id` из сессии вместо значения из
  `localStorage`. Реальная защита — Шаг 26 (см. «Технический долг» выше)
- **Первый живой вход не работал несколько дней после деплоя** —
  диагностировано и закрыто 2026-07-28, три отдельные причины по
  очереди. (1) Caddy держал весь сайт, включая `/auth/vk/callback`, за
  общим Basic Auth — VK обращается на этот адрес не из браузера
  пользователя, поэтому браузерные cached-credentials тут не помогают,
  callback получал `401`; поправлено выводом `/auth/vk/*` в отдельный
  `handle`-блок без `basic_auth` в `/etc/caddy/Caddyfile`, остальной
  сайт по-прежнему защищён. (2) `VK_CLIENT_ID` в проде `.env` содержал
  опечатку (значение отличалось на одну цифру от реального в кабинете
  id.vk.ru) — из-за неё VK не мог показать ничего осмысленного на
  `/authorize`, ещё до захода на callback, ни при каких условиях сети,
  браузера или Basic Auth, что и делало диагностику такой долгой. (3)
  После исправления `client_id` обмен кода на токен уже проходил, но
  падал следующий вызов `/oauth2/user_info` (`client_id is invalid`) —
  устранено удалением самого вызова, см. выше. Проверенные, но не
  оказавшиеся причиной гипотезы по пути: смена базового домена в
  кабинете VK, throttling по IP/`client_id`, статус верификации
  бизнес-профиля, уровень конфиденциальности приложения

## Роли и права доступа (Шаг 28)

До этого шага у всех залогиненных через VK ID пользователей были
одинаковые права на все мутирующие эндпоинты — `get_current_user_required`
проверял только личность («это правда ты»), не полномочия («тебе можно
это делать»). «Диспетчер» был чистой договорённостью: пользователь без
`QueuePosition` ни в одной из очередей, не поле в БД.

- **Три независимых булевых поля на `User`** — `is_driver`,
  `is_dispatcher`, `is_admin` (`default=False`), совмещение — просто
  несколько `True` одновременно. Не отдельная таблица связи (как
  `QueuePosition` для очередей): ролей ровно три, они фиксированы, без
  дополнительных атрибутов вроде `position` — булевы поля проще, без
  join'ов, и соответствуют масштабу ~10 пользователей
- **`is_admin` — суперсет**, проходит любую ролевую проверку независимо
  от `is_driver`/`is_dispatcher` — «админ = полный функционал»
- **Роль `driver` — не то же самое, что «состоит в `QueuePosition`»**.
  Роль решает права, `QueuePosition` — текущее операционное состояние
  (водитель может временно не стоять в очереди, оставаясь водителем)
- **Бэкфилл при миграции `338c507c5018`**: кто уже состоял хотя бы в
  одной `QueuePosition` → `is_driver=True`; кто нет → `is_dispatcher=True`
  (сохраняет прежнюю негласную конвенцию). `is_admin` никому не
  проставляется автоматически — курицы-и-яйца нет благодаря
  `scripts/grant_role.py` (см. ниже)

### Права по ролям

- `app/auth.py`: `require_driver`/`require_dispatcher`/`require_admin` —
  поверх `get_current_user_required`, `403` без нужной роли (или без
  `is_admin`)
- `/orders/{id}/self-assign`, `/respond`, `/complete` — `require_driver`.
  Для `self-assign` это отдельный, более общий гейт поверх уже
  существовавшей проверки `QueuePosition` для конкретного `queue_type`
- `/orders/{id}/cancel` — диспетчер и админ обходят проверку
  `created_by`/`assigned_to` целиком, могут отменить **любой** заказ.
  Обычные пользователи — прежняя логика (создатель/исполнитель) без
  изменений
- **Новый `POST /orders/{id}/assign`** (`require_dispatcher`) — прямое
  назначение вне очереди, тело `{"driver_user_id": int}`:
  - целевой пользователь должен иметь `is_driver=True` и `QueuePosition`
    для `queue_type` этого заказа (`400` иначе — тот же принцип, что у
    `self-assign`: диспетчер не может назначить того, кто физически не
    в этой очереди)
  - заказ `pending` → как `self_assign_order`: существующий `pending`
    оффер помечается `declined`, новый сразу `accepted`
  - заказ уже `assigned` кому-то другому (переназначение) → прежний
    исполнитель возвращается **вторым** в очередь (та же вставка после
    текущего первого, что в `cancel_order`) — не по его вине забрали
    заказ, но и обгонять честно первого он не должен
  - в обоих случаях новый исполнитель уходит в конец своей очереди
    (`max position + 1`, тот же приём, что в `respond_to_order`/
    `self_assign_order`)
  - `notify_assigned` (`app/notifications.py`) и `_log_activity` с
    `event_type="order_assigned"`
- `POST /orders` (создание) и `/price` (CRUD) — роли не сужают, остаются
  доступны любому залогиненному (осознанное решение — не убирать
  существующие возможности без явного запроса)
- `GET /me`/`GET /users` — отдают `is_driver`/`is_dispatcher`/`is_admin`
  в ответе (нужно фронтенду для условного UI)

### Admin-only API

Веб-аналог `scripts/add_user.py`/`scripts/reorder_queue.py`, всё за
`require_admin`:
- `POST /admin/users` — создание с ролями и (опционально) сразу в конец
  указанных очередей
- `PATCH /admin/users/{id}/roles` — частичное обновление ролей
- `POST`/`DELETE /admin/users/{id}/queue/{queue_type}` — добавить/убрать
  из конкретной очереди без пересоздания пользователя
- `POST /admin/queue/{queue_type}/reorder` — переставить порядок, та же
  валидация «ровно тот же состав», что в `reorder_queue.py`

### Страницы «Пользователи» и «Админ»

- `static/users.html`/`users.js` — список всех, роли бейджами
  (`.role-tag-driver`/`-dispatcher`/`-admin`, по образцу
  `.type-tag-long`/`-short`). Видна любому залогиненному, не только
  админу — обычный `#auth-gated`/`#login-prompt` каркас
- `static/admin.html`/`admin.js` — второй уровень гейта поверх обычного:
  сессия есть, но не `is_admin` → «Доступ только для администратора»
  вместо форм. Три секции: добавление пользователя, чекбоксы ролей на
  каждой строке (сразу шлют `PATCH` при клике), порядок очереди
  (кнопки ▲/▼ вместо drag-n-drop — проще и одинаково удобны на телефоне)
- `nav.js`: пункт «Админ» — не в статичном `SITE_PAGES`, добавляется
  вторым проходом на `DOMContentLoaded`, когда `window.sessionReady`
  подтвердит `is_admin` (к этому моменту все синхронные `<script>`,
  включая `session.js`, уже выполнены — гонки нет)
- Дэшборд (`static/index.html`/`dashboard.js`): у диспетчера/админа на
  заказах в «Ожидают ответа» появляется контрол «Назначить» (`<select>`
  водителей текущей очереди + кнопка), не заменяющий обычные
  accept/decline/self-assign. Новая секция «Все активные заказы»
  (только для dispatcher/admin, `GET /orders?status=assigned` без
  `user_id`) — обзор всех назначенных заказов с тем же контролом как
  «Переназначить» и «Отмена заказа» на любом из них

### CLI-скрипты — остаются, не только UI

- `scripts/add_user.py` — без флагов даёт `is_driver=True` (как и раньше
  ставил в обе очереди по умолчанию), `--no-queue` — `is_dispatcher=True`
  вместо голого «без очереди»
- Новый `scripts/grant_role.py <username> driver|dispatcher|admin
  [--remove]` — точечно включает/выключает одну роль. Основной инструмент
  для выдачи первого `is_admin` после деплоя миграции (курицы-и-яйца:
  без этого некому было бы открыть «Админ»), и общий break-glass путь на
  будущее, если веб-интерфейс/сессия недоступны

## PWA (Шаг 30)

Цель — устанавливаемость на домашний экран телефона и полноэкранный
режим без адресной строки, **не** офлайн-работа с данными: очередь и
заказы — живые операционные данные, показать водителю устаревшую
офлайн-копию (кто сейчас первый, какой заказ ещё `pending`) реально
опасно для бизнеса, не просто неудобно.

- Фундамент уже был готов после «Адаптивного favicon» — иконки, полный
  `site.webmanifest` (`icons`/`theme_color`/`display: standalone`),
  `<link rel="manifest">` на каждой странице. Не хватало service worker'а
  — без него часть браузеров не считает сайт «устанавливаемым»
- `static/sw.js` — кэширует **только** статику (`/static/css/`,
  `/static/js/`, `/static/fav/`); HTML-страницы и все API-запросы не
  трогает вообще (`fetch` не вызывает `respondWith` для них, запрос
  идёт как обычно)
- `GET /sw.js` (`app/main.py`) — отдаёт файл из `static/sw.js`, но с
  корня, не из `/static/`, чтобы scope service worker'а по умолчанию
  покрывал весь сайт (`/`), а не только `/static/*`. Явный
  `media_type="text/javascript"` — без него браузер может отказаться
  регистрировать SW при неверном Content-Type
- **Стратегия — stale-while-revalidate, не чистый cache-first (с
  0.4.2).** Отдаём закэшированный файл сразу, если он есть, но
  параллельно (в `event.waitUntil`, чтобы браузер не оборвал запрос
  сразу после ответа) всегда идём в сеть и обновляем кэш для
  следующего раза. Чистый cache-first требовал вручную бампать
  `CACHE_NAME` при каждом изменении `style.css`/`*.js` — на практике
  это один раз забыли сделать (0.4.1, фикс ролей в `session.js`), и
  пользователь застрял на старой версии на обычной навигации по
  ссылкам (`Ctrl+F5` помогал — это браузер целиком обходит service
  worker на жёсткой перезагрузке, не код этого файла). Теперь свежая
  версия подхватывается сама, максимум одна лишняя загрузка — без
  необходимости помнить про версию вообще
- `CACHE_NAME = "carpool-static-v2"` — по-прежнему меняется вручную
  при желании принудительно сбросить весь кэш разом (`activate`
  удаляет все кэши с другим именем), но это уже подстраховка, а не
  единственный механизм свежести
- Регистрация — одна строка в `nav.js` (уже подключён почти на каждой
  странице), не в каждом HTML-файле по отдельности
- `site.webmanifest` дополнен `scope`/`lang`/`description`
- Проверено вручную (dev-сервер): service worker регистрируется и
  активируется, в `Cache Storage` после обычных загрузок оказываются
  только статические файлы (`/users` и `/` в кэш не попадают);
  подмена закэшированного файла на заведомо устаревший показала, что
  первый запрос отдаёт его как есть, а фоновое обновление (защищённое
  `waitUntil`) доезжает до конца и кладёт в кэш актуальный файл ещё до
  следующего запроса
